# Vois Evaluation Harness

A scenario set for checking whether a screen generated with the `vois-*` skills actually followed the decision layer (`vois-components`' job trees, `vois-patterns`' path trees), not just whether it used the right tokens.

## What this is not

Not a new rule format. `scenarios.json` doesn't invent a YAML scenario schema — a scenario is just an existing `components-rules.json` job's `condition` paired with its `recommendation` (renamed `expected_outcome` here) and the near-miss outcomes its own `rationale` already rules out (`forbidden_outcomes`). If a scenario's expected outcome looks wrong, the fix is in `components-rules.json`'s decision tree, not in this file — this file only restates it for testing purposes.

Not a scored, weighted rubric yet. `score_categories` names the dimensions a run can be judged on (token/component/pattern/visual/decision-layer/anti-pattern/accessibility adherence), but none carry a weight. Assigning percentages to categories with zero scenarios run yet would be inventing numbers exactly the way `vois-tokens` warns against inventing token values — see `score_categories_note` in `scenarios.json`.

Not automated for the 55 scenarios in `scenarios.json`. Their expected outcomes are prose, so running one still means: hand its `user_prompt` to an agent with the `vois-*` skills active, let it build the screen, and check the result against `expected_outcome` and `forbidden_outcomes` by hand. The tasks in `lookalike-pass/` and `tasks/` are different: they carry checks a script can run, and `run/run.mjs` runs them (see "Running the task runner" below).

## Coverage

All 21 jobs in `components-rules.json` have at least one scenario: 55 in total. Each one names its branch of the job's decision tree with `tree_path` (indexes into `decision_tree`, then `sub_branches`). `node check-scenarios.mjs` fails if a scenario's `condition` is not that branch's text word for word, if its `expected_outcome` does not start with the tree's recommendation (up to the first bracket or dash, ignoring case and punctuation), or if a job or score category does not exist. It runs in CI, so a tree change that makes a scenario stale shows up as a failing check.

Scenarios EVAL-014 to EVAL-053 were written for the 15 jobs that had none, EVAL-054 was added afterwards for the back link branch, and EVAL-055 for the mobile filters branch of `JOB-OVERLAY-INTERACTION`. Not every branch has one: 54 of the 99 branches that recommend something do, and the checker prints that count. The gaps include the Plain and Alert branches of the empty-content job, the Table, Tabs and Card branches of the data-visualization job, and the Input, Radio and Command branches of the text, binary-choice and list jobs.

## Running the task runner

`run/run.mjs` takes the lookalike prompts (`LP-*`, `HP-*`) and the design tasks in `tasks/design-tasks.json` (`DT-*`), builds each screen with the `claude` CLI, and scores the TSX with scripts. It runs every task with the skills on and with them off, several times each, and writes one results file to `results/`.

```
node vois-eval/run/run.mjs --dry-run                                   # show the plan, call nothing
node vois-eval/run/run.mjs --model claude-sonnet-5-5 --samples 3        # all tasks, both conditions
node vois-eval/run/run.mjs --model claude-haiku-5-5 --tasks DT-01,DT-04 --samples 1 --smoke
```

It calls a model, so it costs money and is run by hand, before a release or after a change to a skill. CI never runs it. `--model` is required, and should be the full model id (not an alias like `sonnet`), because the results file records which model produced it and the runner checks that the model that answered is the one you named. `--samples` defaults to 3, because one sample per prompt says nothing about variance. `--budget` caps the cost of each call (default $1) and `--max-turns` its turns (default 40).

**The two conditions.** *On*: the run directory holds a copy of `vois-patterns`, `vois-components`, `vois-tokens`, `vois-dataviz` and `righter` from this checkout under `./skills`, and the prompt says they apply and where they are. That pins the skill version under test; the skills are checked once before the plan starts, so a copy that comes out without its `SKILL.md` stops the run before anything is spent instead of turning every skills-on sample into an error. *Off*: an empty directory and the baseline prompt that forbids reading skills.

**If a run dies.** Every finished sample is appended to a progress file (`--progress <file>`, default a new file in the system temp folder; the path is printed at the start), after a header that pins the model, samples, tasks, conditions, turn limit, git sha and status, and skill versions. To continue a run that was cut off, repeat the same command with `--resume --progress <that file>`: only the missing samples are run, and the run keeps its original start time. A resume is refused if anything in the header differs, or if the file has a sample twice or one that is not in the plan. A torn last line is dropped. A progress file is never reused without `--resume`, and `--force` never overwrites one. Samples that ended in an error stay as they are on a plain resume. Add `--retry-errors` to run them again: their lines are dropped from the progress file (rewritten whole, then renamed, so a crash cannot leave it half written) and only those samples are run.

**When samples fail.** A run stops itself after 5 samples in a row end in an error, because when the account hits its usage limit, or the service is down, every remaining sample fails the same way. It then writes no results file, saves what it has to the progress file and prints the exact command to continue (`--resume --retry-errors --progress <file>`). A usage limit resets on its own, so wait for it. If errors are scattered and the run finishes, the file is written but marked `full: false` and named `...-partial.json`, so it is kept but never compared, and the runner says which command re-runs just the failed samples. A run with no errors that covers every task and both conditions is the only kind marked full, and the checker refuses a full run that contains an error sample. This exists because the first full Sonnet run hit the account's usage limit at sample 187 and the other 84 failed instantly; before this, that run would have been written as an ordinary results file with a pass rate dragged down by errors that had nothing to do with the skills.

**What is and is not isolated.** Both conditions get the same four tools (Read, Write, Glob, Grep), no MCP servers (`--strict-mcp-config`) and project-only settings. That removes the Skill tool, skill listing, the shell and MCP tools. It matters: in a probe with the CLI's default tools and project-only settings, the agent still listed the account's installed Vois skills. It does **not** sandbox files. Read and Glob accept absolute paths, and the user's own `CLAUDE.md` memory may still load (I have not tested that, and the runner does not control it). The off prompt only asks the agent not to read skills. So the runner logs every tool call, and each sample records `outside_cwd_access`: the paths its file tools touched outside the run directory (a `~` path or `~name` counts as outside, and every `{a,b}` alternative of a glob is checked). If an off sample has any, check it did not read installed skills before trusting the off rate. `check-results.mjs` warns about them and the run summary counts them as `outside_access`. If a memory file mentions Vois, nothing here would show it: run on a machine whose user-level memory says nothing about Vois, or the off rate may be too high. Each results file lists these settings under `isolation`, and the list is built from the same constants as the flags the CLI is started with.

**What a pass means.** A sample passes when all of these hold: it imports one of the task's `expected_imports`, imports none of its `forbidden_imports`, the lookalike scanner (`lookalike-pass/scan.mjs`) finds nothing, and every `required_patterns` regex matches while no `forbidden_patterns` regex does. Comments are removed first by a small scanner, so naming a component in a comment does not count (including a trailing `// note` after a word or number), and text that only looks like a comment (`<p>Press // to search</p>`, a URL, `"components/*"`, `src/*` in JSX text) is kept. Known gaps: JSX text on its own line that contains ` // ` loses the words after it, and a `//` right after a closing quote is always read as a comment. Patterns run on lines cut to 4000 characters, because two of them scan a line twice. The `vois-tokens` and `vois-dataviz` detector findings are recorded in each row but do not decide the pass, because those detectors are advisory.

**Runs that stop early.** A run that hits the turn or budget limit, or the 15-minute timeout, is scored on whatever screen it had written and marked `truncated` (with `stop_reason` saying which), because a skills-on agent reads many files first and would otherwise be marked down for it. The summary counts them and `check-results.mjs` warns, so compare the on and off counts before reading the rates. Any other CLI error, a timeout, or an agent that wrote no code is an error row: it counts as a failed sample and is reported separately, so an outage cannot make a run look better. A timeout or a missing result event also marks the sample `cost_unknown`, which makes the cost total a lower bound. A missing result event without a timeout (the CLI crashed) is an error row. A sample is marked `model_mismatch` when the CLI reports no sign of the model you named (it can fall back to another on overload). A context-window suffix such as `[1m]`, an 8-digit date on the id, and a helper model listed next to the named one do not count. A run with mismatched samples cannot be compared, so `check-results.mjs` **fails** on it and says to redo the run or remove the file, because otherwise the regression check would quietly not run for that model. The CLI lists a small helper model next to the one you named on every call, so a set of two models is normal and not reported. A sample whose set of models differs from the run's usual one (an extra helper, or a fallback after the named model answered), or that reports none at all, is a warning, not a failure, so look at it before trusting the rates.

**What it does not measure.** It does not render anything, so layout, spacing, contrast and interaction are not checked. The pattern checks are heuristics read from the rules named in each task's `source_rules`: a pass means the obvious failure did not happen, not that the screen is good. The `DT-*` tasks are marked `review: unreviewed`, because a designer has not yet signed off on their expectations; treat their rates as provisional until someone has. There is no LLM judge.

**The results file** (schema `vois-eval-results/1`) is named `results/<date>-<model>.json`, with `-smoke` or `-partial` added for those runs and `-2`, `-3` for a later run on the same day; the runner never overwrites an earlier file, even when two runs finish at the same moment (`--out` with `--force` is the one way to replace a file on purpose, and a file that appears at `--out` during a run is left alone and the results go to the next free name). It records the model, when it was made, the `claude` CLI version, the git sha and whether the working tree was dirty (the skills are copied from the working tree, so a dirty tree is not reproducible from the sha; the sha and the dirty state are taken at the start, and a change to the repository during the run also counts as dirty), the isolation settings, the version of each skill under test, every sample with its score, cost, duration and flags, and a per-condition summary.

**What CI checks.** `check-results.mjs` checks each file's shape, that nothing is missing or duplicated, that `pass` and `decision` agree with the listed findings (a sample cannot be marked as passing with a failure listed), that `model_mismatch` and `truncated` agree with `served_models` and `stop_reason`, and that the summary matches the samples. It reads committed JSON, so it catches mistakes and careless edits, not a deliberate one: `full`, for example, is the runner's word, and the check cannot prove a run really covered every task. A results directory that is missing is an error, not a pass. Then, for each model, it compares that model's newest **full** run with the full run before it, and fails if the skills-on pass rate fell by more than 10 points over the tasks they share. A run is full only if it covers every default task with both conditions (`full: true`); a run with `--tasks`, `--limit`, one condition or `--smoke` is kept but never compared. Runs are ordered by their `created_at` time, which is also where `date` comes from, so a run that crosses midnight still validates. The newest run is compared with the newest earlier run that can be compared, so one run that had to be skipped does not leave the next with nothing to compare against. A comparison is skipped, with the reason printed, when the samples per task differ or when fewer than 5 tasks are shared. Those two are notes, not failures, so a deliberate change of sample count does not break CI, but it also means that run is not checked. The output also shows how many skills-on samples were truncated in each run, because a skill change that makes the agent read more files first can lower the pass rate through truncation rather than through worse decisions.

`node --test vois-eval/run/run.test.mjs` tests the scoring, task loading, results checks and run loop. It uses a stand-in for the `claude` CLI (`run/fake-claude.cjs`) for the parts that touch the CLI, so it costs nothing.

## The first full baseline (Sonnet, 2026-10-26)

`results/2026-10-26-claude-sonnet-5-5.json`: 45 tasks, both conditions, 3 samples each (270 samples), `claude-sonnet-5-5`, the skills as of `vois-components` 1.15.2, `vois-tokens` 1.23.2, `vois-dataviz` 1.1.2, `vois-patterns` 1.17.0 and `righter` 1.10.0, on a clean checkout at commit `f884f71`. No sample errored, was truncated, or was answered by another model. It cost about $34 ($28.94 with the skills on, $5.31 off).

It was not one uninterrupted run. The account hit its usage limit at sample 187 and the remaining 84 samples failed at once. That output was thrown away; the 186 good samples were kept and the 84 were run again after the limit reset, through `--resume`, from the same commit with the same header. The `claude` CLI version in the file was read when it was written, so the first 186 samples may have run under an earlier CLI patch version than the one recorded.

| | skills on | skills off |
|---|---|---|
| All 45 tasks | 125 of 135 pass (0.93) | 85 of 135 (0.63) |
| 30 `LP-*` prompts | 88 of 90 | 71 of 90 |
| 10 `HP-*` prompts | 30 of 30 | 10 of 30 |
| 5 `DT-*` tasks | 7 of 15 | 4 of 15 |

Per task, skills on did better on 18, the same on 26 and worse on 1 (DT-02, one sample, which the scanner flagged as `fake-tabs` on a form; the screens were not kept, so I could not look at it). Skills on cost about 5.5 times as much per sample ($0.214 against $0.039) and used about 4 times the turns (8.6 against 2.0), because the agent reads the skills first.

**How far to trust it.**

- **The `LP-*` and `HP-*` result is in-sample.** The lookalike table and the scanner's signals were derived from blind builds of these same 40 prompts, so the skills were taught the failures this score looks for. Of the 39 skills-off failures on these 40 prompts, 24 contain a raw palette colour such as `bg-green-100` (15 of them only that), 22 contain another known lookalike (fake avatar, hand-ringed button, toast, progress bar, alert, native dialog, `title` tooltip), and 2 did not import the expected component. A high score here says the skills prevent those known failures. It does not say they generalise.
- **The `DT-*` tasks are the only fresh test, and there are 15 samples per condition.** Two of the five are not clean. **DT-03 was mis-specified** and should be ignored: it asked for 12 weeks, `vois-dataviz` sends "about 12 or fewer" periods to a column chart, and the check demanded a line, so skills-on agents were marked down for what the skill says to do. All three skills-on samples drew the channel bars and none drew a line or area for the trend; I infer they used columns, as the skill directs, but the screens were not kept, so I did not see them. It is replaced by **DT-06**, which asks for a year of weekly data. **DT-04** (mobile filters) failed in all six samples, but the file predates the rule that settled Drawer over Sheet (`vois-components` 1.17.0). The record says only that no sample imported a Drawer. It cannot say what they used instead, because the generated screens are not stored.
- The remaining three (DT-01, DT-02, DT-05) went 7 of 9 with skills on and 4 of 9 off. That is a direction, not a measurement.
- Skills on still produced a `fake-avatar` (an initials circle) in 2 of 3 samples of LP-05a, which is a gap in the skills, not noise.
- The checks are heuristics and have not been reviewed by a designer. Passing means the obvious failure did not happen.

The next full run of this model will be the first one the regression check can compare against this one. The `DT-03` results in this file should be excluded when it does.

## Using a run's results

A scenario run tells you two different things, and it's worth keeping them separate:

- **A wrong outcome** (the agent picked a `forbidden_outcomes` entry, or missed `expected_outcome` entirely) means the decision layer wasn't followed. Check whether the rule was legible where the agent would have found it — sometimes this is a prompting/routing problem (the agent never reached `vois-components`), not a content problem.
- **A right outcome by luck** (matched `expected_outcome` without any evidence the agent consulted the relevant job) doesn't validate the decision layer either — it just means the obvious answer and the correct answer happened to coincide this time. Scenarios here were picked because their `forbidden_outcomes` are plausible enough that a naive agent could land on them, but that's not a guarantee for every prompt phrasing.

## Where this fits in the design-intelligence-layer plan

This harness is Phase 5 of that plan (`design-intelligence-layer-prd.md`). Phase 6, the iteration loop, is: run these scenarios, find where a rule is missing or unclear, fix it in the *existing* skill file it belongs to (not a new parallel file), re-run. Nothing in this folder replaces that loop — it just gives it something concrete to run against.
